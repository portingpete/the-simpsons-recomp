# Native D3D11 resource backend

`renderer/native_backend.cpp/.h` implement real native D3D11 device creation,
owned immutable RGBA8/BC1/BC2/BC3 textures, shader-resource views, vertex/index
buffers, staging readback, and optional HWND swap-chain attachment. The immediate context has one explicit
owner thread. Upload input is consumed immediately; resources retain native COM
ownership rather than guest pointers. Cross-device use fails explicitly.

This library is now linked to the game runtime. The verified engine request-2
entry allocates actual native backing and attaches the original window, then
fails before readiness because the complete engine services are not yet wired.
`VdInitializeEngines` remains unimplemented and is no longer executed by this
native start path; no console D3D object or GPU command processing is provided.
The four screen shaders now have original-byte arithmetic proof and native
implementations. Engine resource/plugin callbacks, effective inherited draw
state, camera lifecycle and presentation still require the native bridge.

The Windows API contracts were checked against
[D3D11CreateDevice](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-d3d11createdevice)
and [CreateSwapChainForHwnd](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nf-dxgi1_2-idxgifactory2-createswapchainforhwnd).
The candidate native presentation target is two-buffer BGRA8 UNORM with vertical
sync; its color/gamma compatibility with the original engine remains a bridge
verification requirement. Native presentation count is separate from new game
frames; headless resource checks increment neither. Occluded presentation is
not counted as a shown frame. Swap-chain attachment was exercised by the
original executable in boot024. No original presentation has occurred.

`NativeGraphicsResources` tests a non-square, non-aligned-row RGBA surface,
all three compressed storage types, copied upload ownership, staging pitch,
resource lifetime after the original host reference is dropped, invalid bounds,
cross-thread rejection, and cross-device rejection. It passes with native WARP.

The independent hardware run also passes at feature level `0xB100` (11.1):

```powershell
.\build\native\NativeGraphicsTests.exe --hardware
```

Its log is `build/native-graphics-hardware.log`. Byte-identical GPU resource
roundtrips establish storage behavior; they do not establish original shader
sampling, framebuffer appearance, or gameplay. No original game frame has been
rendered by this backend.

## Original screen material equations on native D3D11

`renderer/screen.hlsl` implements the proven equations in
`docs/screen-shaders.md`: position `(x,y,0,1)`, flat RGBA constant, and sampled
RGBA multiplied component-wise by the color constant. It also explicitly
implements the helper's GREATER alpha test as a post-color discard. The caller
supplies its enable and reference value. FXC compiles four Shader Model 5 entry
points during the build, with strictness/IEEE flags; the executable links no
shader compiler. Generated byte-array headers live in `build/shaders`.
This follows Microsoft's [build-time shader compilation contract](https://learn.microsoft.com/en-us/windows/win32/direct3dhlsl/dx-graphics-hlsl-part1).

The bounded `drawScreen` service takes owned vertex/color values, a retained
native texture, original blend selector 0..3, an explicit effective sampler,
alpha-test settings and color write mask. It uses the complete target as viewport,
disables depth/stencil and culling, and rejects unsupported/nonfinite input.
**A game bridge may select this pass only after proving those effective states.**
It does not silently supply the original helper's unresolved inherited state.
RGBA8/16-float/32-float offscreen target formats are native storage services;
none is asserted to equal the game's packed startup target representation.
The subsequent exact format decode in `docs/native-driver-state.md` identifies
the startup color as 10:10:10:2 UNORM, not 7e3 floating color.

`NativeScreenShaders` executes on real D3D11 and checks flat HDR/negative RGB,
all four recovered blend equations with independent alpha, channel masks,
strict alpha-threshold edges, half-target quad coverage, asymmetric 2x2
RGBA sampling/multiplication, normalized repeat and bilinear averaging. It
also rejects cross-device resources and invalid submissions without incrementing
draw counts. All fixture pixels are staging-read and checked; none is presented.
It passes with WARP and hardware feature level 11.1:

```powershell
.\build\native\ScreenShaderTests.exe --hardware
```

The log is `build/native-screen-hardware.log`. These checks validate native
implementation of the recovered equations, not Xenos-versus-native rounding,
original target conversion, menu rendering or gameplay. Draw submissions and
presentations have separate counters; an original game-frame counter awaits
engine presentation integration.

Buffer tests use the recovered startup sizes `4E20`, `1FFFE` and `40000` bytes.
Partial uploads preserve unrelated bytes and snapshot source data on return;
range overflow and cross-device operations fail. The bridge must convert
original index/vertex data to the proven native input layout before upload.

## Verified startup resource ownership

The native color service now includes actual `R10G10B10A2_UNORM` RTV/SRV
resources. Depth uses `R32G8X24_TYPELESS` backing with a D32/stencil view and
separate depth/stencil sampling views. Clear/readback tests preserve exact
20e4 values, including 2^-34, and all eight stencil bits. Clear values that
would require an unverified rounding choice fail explicitly. Native general
depth rasterization/resolve is not enabled by this allocation service.

`StartupResources` owns six distinct target roles and five required buffers.
Initialization publishes the bundle only after every allocation succeeds and
matches its required type/size. Failed replacement preserves the prior bundle.
The tests inspect actual backing by clearing/uploading different data to each
role before reading all of them, then exercise 66 injected allocation-failure
paths, incorrect/aliased factory results, retained-resource lifetimes and reset.
Both WARP and hardware pass; the hardware log is
`build/native-driver-resources-hardware.log`.

Boot024 through boot028 prove this allocation component runs from the actual
original engine request, with original CPU pools, native scratch/declaration
ownership, state caches and dynamic buffers now initialized and unwound.
At those milestones, persistent ownership and original plugin construction
were still unimplemented; no original frame was published.

Boot029 additionally binds the real default color/depth attachments before the
CPU initialization. `target_bindings.cpp` validates device, backing, dimensions,
sample count and distinct color slots before calling D3D11, then queries the
actual retained views because OMSetRenderTargets has no HRESULT. It does not
clear, select a viewport or draw. Headless WARP and hardware tests cover valid
single/multiple/depth-only/unbound selections and rejected incompatible resources.
Bindings are cleared during startup unwind. Boot030/031 add persistent ownership
and checked target-role publication; all original plugin constructors and gamma
initialization now complete. Actual startup stops at post-start console-device
integration `823EE8F8`. See native-driver-lifecycle.md for paired stop, restart,
failure rollback and the nineteen passing suites. No game frame has rendered.

`NativeMaterialCompiler` connects the immutable original-record owner to real
D3D11 shader object creation using the four offline screen bytecodes. Creation
of an engine material does not falsely publish compiled readiness. First bind
either acquires the matching real native artifact or rejects an untranslated
record explicitly. The native tests create all four actual screen artifacts
and reject all sixteen unimplemented startup shaders; no shader interpreter or
runtime shader compiler is linked. Original engine create/release services now
have checked native ABI hooks and run under the actual original plugin walk.
Native binding/draw services remain incomplete; explicit guards reject original
SDK consumers before they can use native IDs as SDK object pointers.

Boot032/033 add original binding reset, checked native context identity and
native submission registration while retaining both original CPU allocations.
Boot034/035 create the original camera/shared-depth rasters through native
platform callbacks and original CPU allocation/plugin/list services. Build062
passes 22 suites. Camera begin, target/viewport integration, texture loading and
draws remain unimplemented. See native-camera-raster-bridge.md.
